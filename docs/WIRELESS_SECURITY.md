# WirelessLab security review

Only generated fixtures and explicitly authorized local captures are in scope. No traffic collection, password extraction, credential attacks, jamming, real interface configuration or Cisco device control is implemented. Generated EAPOL payloads contain zero placeholders, not secrets.

Guest cookies are server-generated random values, HttpOnly/SameSite Strict, Secure under HTTPS, one hour. Database stores SHA256 hashes. All run/AP/history/exports require ownership. Cross-session run reads return 404. Mutation requests require a custom header plus an allowed browser Origin; no wildcard CORS is added. New API responses are no-store. Expired data is removed on the next admission; physical deletion is not promised at the exact expiry second. Ending a demo immediately deletes its rows.

Guests cannot upload captures or invoke arbitrary analyzers, commands, paths or interfaces. The approved registry alone selects scenario fixtures. Upload ingestion exists only for a socket-loopback operator with `WIRELESS_ALLOW_UPLOADS=true`, a >=24-character `WIRELESS_UPLOAD_TOKEN` supplied in a matching header, and `X-Lab-Authorized: true`. Do not configure these variables on public demos or expose the token in frontend code. A reverse proxy that turns remote clients into loopback peers must not enable this local path. Uploaded files default to per-file MAC/SSID pseudonyms; raw bytes are deleted with the temporary directory, but metadata and classification can still be sensitive. Guest capability discovery always reports uploads disabled.

Input bounds: 1 MiB PCAP/PCAPNG, 5000 packet rows, 50,000 analyzer records, 80-character identifiers, 1024-byte TSV lines; execution timeouts of 10 seconds for first field discovery, 12 seconds for extraction, eight seconds for C++. Outputs are checked after subprocess completion (not a streaming memory sandbox). Four concurrent scenario pipelines and per-owner quotas bound ordinary guest work. Local operator upload parsing has the same per-file and time bounds but does not share the scenario semaphore. Admission cap is 128 sessions per worker and 10 creations/minute/socket peer; expensive operations are 12/minute/guest. Persistent 20-run histories and eight APs bound storage. Multiple workers require shared admission/concurrency controls before public scale.

TShark is a complex native parser: use a patched supported distribution, restrict the local upload feature, run as nonroot and without network capture capabilities. Docker runtime uses `appuser`; no NET_ADMIN, host network or privileged mount is added. A malformed capture returns a generic error without raw subprocess stderr. Audit logs include only run ID, finite scenario and verdict; metrics never label identifiers or cookies. CSV export fields are numeric or validated safe identifiers.

## Dependency review

Actual JSON scan reports live in `wireless-lab/evidence/*audit*.json`. The pinned backend requirements scan completed without known advisories at evaluation time, including resolved transitive packages in the full report. Production npm scan has no vulnerabilities. The initial full npm scan found 10 development-tool advisories, including critical Tinypool and high Tailwind transitive findings. Updating Vitest to 5.0.5 removed the critical Tinypool findings; the final full scan reports seven development advisories (five high, two moderate), all in the retained Tailwind 3 tool chain. Tailwind 3 transitive development advisories are retained and explicitly surfaced by the non-blocking CI report; production builds do not ship these build tools. This is not an assertion of zero project risk or a formal penetration test. Never publish the Vite development server as the public demo; serve the built static assets through the existing web container.
