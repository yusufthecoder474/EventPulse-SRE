# Ten Cisco interview questions, grounded in V3

1. **How does a client join Wi-Fi?** Discovery, authentication, association, key establishment and then IP services are separate stages. In A the generated trace shows association; E and F model later DHCP/DNS failures. Joining does not prove internet access.
2. **Why can a Windows capture lack association frames?** Ordinary interface captures may expose Ethernet-style packets without monitor-mode management evidence. V3 reads the link type and reports the exact unavailable-evidence warning; adapter/driver support is not assumed.
3. **How do you identify WPA2 messages?** Pairwise Key Information flags, directions and replay counters identify M1–M4. V3 does not use packet position alone and corrects an ambiguous TShark M2/M4 heuristic in the generated zero-key-data fixture.
4. **Does HANDSHAKE_COMPLETE mean the password is correct?** No. It means the four modeled headers are present, ordered and replay/role-consistent. The implementation never reads MIC/nonce/key material or proves key installation, security policy or crypto correctness.
5. **Missing message versus timeout?** A short incomplete capture stays incomplete. Timeout requires an observed interval beyond the configured window, and still does not prove the device's internal timer or an incorrect credential.
6. **How do you correlate concurrent clients?** C++ indexes client/authenticator pairs and replay epochs within a window. More than one compatible attempt is marked ambiguous rather than forced together. Active candidates are capped at 64 per pair.
7. **What is a retransmission here?** Repeated stage/counter/role-consistent metadata is a possible retry. Payload/nonce equality is not checked, so it is not a byte-identical retransmission claim. P07 and C++ tests exercise this boundary.
8. **How do you debug a stale dashboard?** Compare explicit AP/client/controller/dashboard observations, timestamps and event IDs. C02 shows AP/client disconnected while controller/dashboard remain connected; delayed synchronization is an evidence-supported hypothesis, not a vendor diagnosis.
9. **Why C++ and Python?** C++ owns deterministic bounded state analysis with STL/RAII, CMake, CTest and executed sanitizers. Python handles maintained TShark extraction, validated schemas, pseudonyms, API orchestration and machine-readable plans. React displays actual results.
10. **How do you prove the feature works?** Run baseline/regression tests, all 24 registered scenarios, deterministic replay comparison, 120 held-out synthetic variants and real browser import/plan flows. Inspect actual CI and artifact links; never generalize synthetic matching to field reliability or hardware support.

## Short project explanation

“I extended an existing reliability platform with a wireless investigation module. Python validates and privately imports small PCAP/PCAPNG files through TShark, then a separate C++17 engine correlates observed WPA2 key-message headers and explains missing or unexpected evidence. I also model client, AP, controller and dashboard views so stale management state can be reproduced without pretending to have Cisco hardware. A registered 24-case plan reuses the original scenarios, adds handshake and controller cases, and exports expected-versus-observed results. I verified parser boundaries, guest isolation, C++ transitions, sanitizers and browser workflows, and kept the original monitoring and recovery regression checks. Real captures, RF behavior and WPA3 interoperability still require a proper authorized lab.”
